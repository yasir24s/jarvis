# Voice spike: Kokoro-82M and F5-TTS in Swift

Measured on 1 October 2026 for D-48, D-52 and D-53, on this Mac: Apple M2 (Mac14,7), 8 GB,
macOS 27.2 (26B5091g), Xcode 27.0, Swift 6.4. The spike is a standalone SwiftPM package at
`~/jarvis-spikes/voice-swift/`, outside the repository. Models, the reference clips and the
samples stay under `~/jarvis-spikes/`. This report is the only file from the spike in the
repo, and nothing was added to `native/Package.swift`.

**Decision (D-54, plan README):** after hearing the samples, the user chose the
short-reference F5 clone as JARVIS's voice despite its latency. The recommendation below is
the spike's own, written before that choice.

## Summary

Kokoro was measured in the first half. F5-TTS was measured in the second, after the user
chose the F5 clone of the reference clip as JARVIS's voice (D-53) and approved the
downloads it needs.

- Kokoro-82M on CoreML through FluidAudio 0.17.4, voices `bm_george` and `bm_lewis`. Once
  warm, one sentence takes 0.085 to 0.30 s to synthesise. The p50 over 20 warm sentence
  calls is 0.147 s, against M8's budget of 600 ms. Real-time factor on whole lines is 0.044
  warm. Peak memory footprint is 538 to 571 MB per process. The first call after launch
  takes 1.2 to 1.7 s, so native needs a warm-up call at launch.
- F5-TTS on MLX (`f5-tts-swift` on mlx-swift 0.29.1, the 8-bit `model_v1_8b` weights) runs
  and clones the clip: eight of its nine samples transcribe back to the intended words.
  Getting speech out of it took four fixes beyond removing the Hub code. The largest:
  f5-tts-swift implements the original F5-TTS, the weights are v1, and two parts of the
  forward pass had to change. It is far too slow for a live voice here.
  With the 10.9 s reference and the default 8 steps, a sentence takes 22.9 to 34.5 s (p50
  27.6 s over 20 calls) and whole lines run at a real-time factor of 5.8 to 7.5. The
  closest setting measured, a 4.28 s reference, has a sentence p50 of 11.2 s, 19 times M8's
  budget. With MLX's default buffer cache the process footprint reaches 5.2 GB; capping
  the cache at 512 MB held it near 1.05 GB between calls (2.1 GB peak) with no measured
  loss of speed.
- Recommendation: the F5 clone cannot be JARVIS's live voice on this 8 GB Mac. Kokoro
  through FluidAudio remains the measured fallback and the only engine here that meets
  M8's budget. Three things need settling for it first: FluidAudio's English frontend
  gives the British voices American phonemes, its G2P files live at a fixed `~/.cache`
  path, and its text normaliser is an 87 MB binary download that this spike left out.

## Kokoro method

F5 used the same method with a few differences, listed under "F5-TTS results".

Each run is one process per engine and voice, started by `measure.sh` under
`/usr/bin/time -l`. The process:

1. reads its own start time from the kernel (`sysctl`, `KERN_PROC_PID`);
2. creates `KokoroAneManager` and awaits `initialize(preloadVoices:)`. Cold start is the
   time from process start to that return;
3. synthesises each of the three lines whole, then each sentence of that line on its own,
   and then repeats the whole set (pass 1, then pass 2 as the warm repeat);
4. writes the pass-2 whole-line audio to `samples/` and one JSON record per run to
   `results/kokoro.jsonl`.

Time to first audio is the wall time of one `synthesizeDetailed` call. FluidAudio returns
an utterance's PCM in one piece, so the first PCM chunk is the whole sentence or line. The
sentence rows are what a sentence-by-sentence streamer would see. Real-time factor (RTF)
is synthesis time over audio duration. Memory figures come from `task_info(TASK_VM_INFO)`
(`phys_footprint`, `ledger_phys_footprint_peak`), `getrusage` and `time -l`. The 1-minute
load average was logged before every synthesis call and before and after every process.

State of the machine: no builds ran during measurement and memory pressure was at the
normal level at the start of every run, but swap already held 7.6 GB of 9.2 GB from the
rest of the session. The 1-minute load average sat between 2.8 and 4.0 from background
work; the busiest processes in a `ps` snapshot were Spotlight, the Claude app and MacPulse.
Run A was the exception: it started at 8.47, about a minute after a build finished.

Compute units were FluidAudio's default for the OS 27 line, `aneTailCpu`: five stages on
CPU and Neural Engine, the noise and tail stages on CPU only. FluidAudio's code notes
intermittent CoreML crashes on the 27 line (issues #843 and #889, reported on iOS). None
happened here in 112 synthesis calls across 7 processes.

## F5-TTS results

### Build

F5 runs through `f5-tts-swift` (last changed 11 December 2024) and `vocos-swift` on
mlx-swift 0.29.1. That tag is the lowest that satisfies both packages (f5-tts-swift asks for
0.18 or later, vocos-swift for 0.29 or later), and it is the version vocos-swift's own
`Package.resolved` pins. Every dependency is a local clone under
`~/jarvis-spikes/voice-swift/deps/`, wired in with `.package(path:)`.

Command-line SwiftPM built it. `swift build -c release -j 3 --product f5-spike` finished
in 284 s on the first attempt. It compiled the nine Metal sources in mlx-swift's
`mlx-generated/metal/` (nine `.air` files in `.build`) into
`mlx-swift_Cmlx.bundle/Contents/Resources/default.metallib` (2.9 MB). mlx-swift's README
says command-line SwiftPM cannot build the shaders. With Swift 6.4, whose SwiftPM built
this package through Swift Build (`.build/.buildSystem_release` reads `swiftbuild`), and
the Metal Toolchain installed, it can; xcodebuild was not needed and was not tried. Later
rebuilds after patches took 10 to 26 s. The binary runs from `~/jarvis-spikes/voice-swift/bin/`
with its two resource bundles beside it: `mlx-swift_Cmlx.bundle` (the metallib) and
`f5-tts-swift_F5TTS.bundle` (F5's mel filterbank).

### Method

F5 follows the Kokoro method, with these differences. `measure-f5.sh` runs each process
under `/usr/bin/time -l` with a 900 s alarm (perl sets it and then execs the spike, so the
alarm lands on the spike). Before and after each process it logs the 1-minute load,
`sysctl vm.swapusage` and `memory_pressure | tail -1`, and it waits up to 10 minutes while
free memory is under 10%. `run-f5-matrix.sh` runs the processes one after another under
the `results/f5-timing` lock, which it takes only once no `swift-build`, `swift-frontend`,
`swift-test`, `swiftpm-testing-helper` or `xcodebuild` process is running.

Each process:

1. reads its own start time from the kernel (`sysctl`, `KERN_PROC_PID`);
2. loads F5 and Vocos from `~/jarvis-spikes/models/` with
   `fromPretrained(modelDirectoryURL:)`, calls `train(false)` on both, evaluates every
   weight, and loads and normalises the reference clip. MLX loads lazily, so without the
   evaluation "ready" would not mean the weights are in memory. Load is this step; cold
   start is process start to its end;
3. makes one warm-up call, "Good morning, sir." This is the first call after launch, the
   one that pays any one-time setup;
4. synthesises the three lines whole and then each sentence on its own, and repeats the set
   as pass 2. The other three runs stop after pass 1;
5. writes the whole-line audio from its last pass to `samples/` and one JSON record to
   `results/f5.jsonl`.

A call is text in, PCM out. The spike calls `F5TTS.sample` itself with
`refText + " " + text` and passes the duration in frames by F5's rule: reference frames,
plus reference frames per UTF-8 byte of reference text times the bytes of new text, over
the speed (1.0). Frames are 256 samples at 24 kHz, 93.75 a second. The 1021 frames of the
10.9 s reference are part of every call: F5 generates the whole mel sequence, reference
included, the vocoder decodes all of it, and the reference part is then cut off. With
`steps: 8`, f5-tts-swift's time grid has 8 points, so `.rk4` takes 7 steps of 4
evaluations. Each evaluation is a conditional and an unconditional DiT pass for
classifier-free guidance, 56 passes per call; `steps: 4` makes 24. Sway is −1.0 and there is
no fixed seed, so each call draws fresh noise; both are f5-tts-swift's defaults. F5 returns
one piece per call, so as with Kokoro the first audio is the whole sentence or line. RTF
and memory are measured as for Kokoro, and MLX's own active, cache and peak memory are
logged at the end of each run.

| A, B | `jarvis_ref_24k.wav`, 10.9 s | 8 | 2 | the primary setting |
| fast | `jarvis_ref_24k.wav` | 4 | 1 | |

### Where F5's memory goes

At ready the process holds 470 to 475 MB, about the size of the two weight files. MLX's
active memory peaks at 1558 MB during a call with the 10.9 s reference and 1093 MB with
the short one, and is back to 442 MB at the end of a run. The footprint does not come back
down. MLX keeps freed buffers in its own cache, and its default cache limit is its memory
limit, 7782 MB on this Mac. In runs A, B and fast the footprint passed 3.0 GB after the
first line and 5.2 GB after the second, and stayed there; the short-reference run reached
4.7 GB by its end. MLX's cache held 4743 MB at the end of each of the first three and
4231 MB at the end of shortref. With the cache capped at 512 MB (run cache512) the
footprint stayed between 1029 and 1085 MB after every call and peaked at 2094 MB, and the
sentence p50 (24.6 s) came out slightly lower than the first passes of runs A and B (26.9
and 25.3 s). That is one process and one pass, but the cap cost no measurable speed.

## Streaming against M8's budget

M8's budget is p50 of at most 600 ms from sentence ready to first audio.

Kokoro streams sentence by sentence and meets it. Across the 40 sentence calls in the
clean runs (both passes), the p50 is 0.147 s and the slowest call 0.30 s. It does not
stream within a sentence: FluidAudio returns the sentence in one piece, and one call is
capped at 510 phonemes and 2000 acoustic frames, so long sentences must be split before
the call. The first call after launch (1.2 to 1.7 s) misses the budget unless native warms
the model at launch.

F5-TTS misses it at every setting measured. It also works sentence by sentence, and each
call generates the whole sentence, reference included, so first audio is the end of the
call. The best sentence p50 was 11.2 s, with the 4.28 s reference. Four steps gave 14.4 s,
and the primary setting 27.6 s over the 20 sentence calls of runs A and B (32.5 s for the
10 in pass 2). The fastest single sentence call took 8.7 s, about 15 times the budget.
Pipelining cannot hide this. Whole lines ran at real-time factors of 2.8 to 7.5, so F5
takes 2.8 to 7.5 seconds to make each second of speech, and a reply of several sentences
would stall between sentences however the work overlaps.

## Recommendation

The F5 clone cannot be JARVIS's live voice on this 8 GB Mac. M8 asks for a sentence p50 of
at most 600 ms; the best F5 setting measured has 11.2 s, and every F5 setting makes audio
more slowly than it plays.

The settings that came closest, against the primary setting (10.9 s reference, 8 steps,
`.rk4`, `cfg: 2.0`: sentence p50 27.6 s, line RTF 5.8 to 7.5, peak footprint 5.2 GB):

| Setting | Sentence p50 (s) | Line RTF p50 | Peak footprint (MB) | What it costs |
|---|---|---|---|---|
| 4.28 s reference | 11.21 | 3.63 | 4710 | A different stretch of the interview as the voice sample, and one word of its transcript taken from the recogniser's first alternative. Its three lines transcribe correctly; how its voice compares by ear is unknown |
| 4 steps | 14.40 | 3.17 | 5228 | Line 3 lost its first words: "As you wish" came back as "He wishes" |
| MLX cache capped at 512 MB | 24.58 | 7.10 | 2094 | No measured loss of speed. It is a memory setting, and any F5 use on this Mac would want it |

Not measured: the short reference with 4 steps, and `cfg` set to 0, which skips the
unconditional pass and so halves the DiT passes per call. As rough arithmetic only, if the
two measured savings multiplied, the short reference with 4 steps would land near 6 s a
sentence, and halving the passes again near 3 s. That is still five times the budget,
before knowing what either change does to the voice.

Memory is the other cost. With MLX's default cache F5 holds 4.7 to 5.2 GB, and run A
pushed swap from 6.4 to 12.9 GB. With the cache capped it holds about 1.05 GB between calls
and 2.1 GB at peak, two to four times Kokoro's 0.54 to 0.57 GB.

Carrying F5 into native would mean mlx-swift 0.29.1 with swift-numerics, the patched
f5-tts-swift and vocos-swift (or a fork with the v1 fixes), the Metal Toolchain on the
build machine, 452 MB of weights, and a cache cap set at launch.

Kokoro-82M through FluidAudio stays the measured fallback. It meets M8's budget with room
to spare once warm, and its samples transcribe back to the right words, but it cannot
clone the reference voice; it speaks with the stock `bm_george` and `bm_lewis` voices. How
native would carry it:

- Package: FluidAudio (Apache-2.0) as a SwiftPM dependency, pinned to 0.17.4, product
  `FluidAudio`, with `traits: []`. That is FluidAudio's own opt-out from its NeMo text
  normaliser, but the manifest still declares the 87.3 MB `NemoTextProcessing` binary
  target, and I did not test whether SwiftPM fetches it anyway. The spike used a local
  clone with that target deleted (seven lines of `Package@swift-6.2.swift`). Native needs
  the same patch, or the user's approval for the download. Without NeMo, English text goes
  through FluidAudio's Swift baseline normaliser. The three lines contain no digits, so
  that path was not exercised.
- Model files, in Application Support rather than the bundle: 51 files, 95.8 MB. The
  7-stage chain with three voice packs is 83.8 MB and the G2P model with its lexicon is
  12.0 MB. The chain accepts a `directory:` argument; the G2P files do not, because
  FluidAudio's `TtsCacheDirectory` fixes them at `~/.cache/fluidaudio/Models/kokoro` on
  macOS. Native needs a small FluidAudio patch there, or a symlink as the spike used.
  Native should fetch the files itself, pinned to the Hugging Face commit `006395f` and
  checked by size, so FluidAudio's own downloader never runs (see run A).
- Memory against the 8 GB limit: 0.33 GB once loaded, 0.43 to 0.49 GB between calls and
  0.54 to 0.57 GB at peak. That is about 1.5 times Python Piper's measured 356 MB peak and
  three to five and a half times the 100 to 180 MB the plan budgets for native Piper.
  Each fresh load measured here took 1.4 to 2.0 s to its first audio (0.2 to 0.3 s to
  load, then the 1.2 to 1.7 s first call), so unloading between turns would put that
  delay back on the next reply.
- Audio format: Kokoro returns 24 kHz float samples. M8's player expects s16le mono at
  22050 Hz (Piper's and ElevenLabs' rate), so it needs a second format or a resample.
- Accent: the American phonemes above. FluidAudio has a per-word override
  (`setEnglishCustomLexicon`), and misaki's British dictionaries (`gb_gold.json` and
  `gb_silver.json`, 6.5 MB together) are in the same Hugging Face repository, but
  FluidAudio does not load them. Not tried.

## What failed, and what fixing it needs

### F5-TTS: four problems between loading the weights and hearing words

The first half stopped F5 before any unapproved download. After D-53 the downloads were
approved, and F5 then failed four times before it produced speech. Each fix is a patch
listed under "F5 patches".

1. MLXNN's `quantize(model:groupSize:bits:)` crashed. The brief's plan was to call it
   before `update`, limited to layers with a `<path>.scales` key. The process died in
   MLXNN's non-throwing `update(modules:)`, a `try!`, with `needModuleInfo("Unable to get
   @ModuleInfo for ConvNeXtV2Block.pwconv2 -- must be wrapped to receive updates")`.
   f5-tts-swift keeps its Linear layers in plain `let` properties and inside `Sequential`
   arrays, and mlx-swift 0.29.1 can only swap a module held in an `@ModuleInfo` property.
   Re-wrapping the properties would not be enough: from reading mlx-swift's
   `update(modules:verify:)`, it also cannot replace one entry of an array such as
   `ff.ff.layers` while leaving the `Dropout` beside it alone (not tried). So the patch
   builds those layers as `QuantizedLinear` (8 bits, group size 64) in the first place,
   while `fromPretrained` builds the DiT from a checkpoint that has `.scales` keys.
   `update(parameters:verify: [.all])` rejects any layer whose form differs from the
   checkpoint, so "quantised exactly where `<path>.scales` exists" is checked at load. All
   166 quantised layers are Linear. The one Linear the checkpoint keeps in float,
   `input_embed.proj`, has 712 inputs, which is not a multiple of 64, and the patch leaves
   it in float by that rule.
2. Two arrays are not in `model_v1_8b`: `melSpec.filterbank` [100, 513] (F5 reads it from
   its own `mel_filters.npy`) and `transformer.text_embed.freqsCis` [4096, 512] (computed in
   `TextEmbedding`'s init). `verify: [.all]` stopped on each with `keyNotFound`. The patch
   keeps the module's own value for any key the checkpoint lacks and prints its name; these
   two are the only ones it prints.
3. The first generation was noise. Line 1 came out as 4.04 s of audio that transcribed to
   nothing, with a flat level between −24 and −34 dBFS and no pauses. f5-tts-swift is a
   port of the original F5-TTS, and `model_v1_8b` holds F5-TTS v1 weights. The shapes are
   the same, so loading succeeded, but the forward pass differs in two places. v1 applies
   rotary position embedding to every attention head; the v0 code applies it to the
   `[batch, frames, heads × 64]` tensor before the head split, so only the first head is
   rotated. v1 also zeroes the filler positions of the text sequence before and after each
   ConvNeXt block. I wrote both changes from memory of F5-TTS v1's model code, which was not
   on this machine, so they are checked only by the result. One build and one generation
   each, all with the reference clip and line 1: dropout off alone left noise (`once-5`);
   adding per-head rotary gave louder audio with pauses but no words (`once-6`); adding the
   text mask gave "Good evening, sir, your battery is at 64%." (`once-7`). The logs are
   `results/f5-once-1.log` to `f5-once-7.log`.
4. Dropout was on. MLX modules start in training mode and f5-tts-swift never calls
   `train(false)`, so the `Dropout(p: 0.1)` in every attention and feed-forward block would
   fire on every call. The spike calls `train(false)` on both models. As item 3 shows, this
   alone did not fix the noise; its effect on speech that already works was not measured.

Two smaller ones:

- The short reference's own transcript drops a word. `SpeechTranscriber` gave "But we were
  friends by that and he's so lovely to work for." for three different cuts of the same
  stretch. Its first alternative for 1.38 to 2.16 s is "that point and", and the
  full-file pass also heard "point". I used the transcript with that alternative: "But we
  were friends by that point and he's so lovely to work for."
- The first primary run started before the rule about the other agent's builds reached me.
  It ran from 11:33 to 11:46 without the lock. No swift or xcodebuild process was running
  when I checked afterwards, and the other worktree's `.build` folder has no files from
  that window, but that agent did write sources and test fixtures in it. I kept that run
  as `A0-prelock` (`results/f5-prelock.jsonl` and `f5-spike_A0-prelock.*`), left it out of
  the tables, and ran A again under the lock.

### Kokoro run A downloaded 42 MB by itself

This was my mistake. I put the four G2P files in `Models/kokoro-82m-coreml/`, but
FluidAudio looks for them in `Models/kokoro/`. When it did not find them, its downloader
fetched its G2P bulk set during run A: the same four files again, plus about 30 MB that
English does not use (`es_lexicon_cache.json`, `fr_lexicon_cache.json`, the `gb_` and
`us_` `gold` and `silver` dictionaries, `config.json` and `vocab_index.json`). All of it
came from huggingface.co/FluidInference/kokoro-82m-coreml, the approved repository. I
deleted the unused files and my misplaced copies. Every later run left the list of model
files unchanged. Run A's 34.3 s cold start includes that download.

Kokoro downloads in total: 100.1 MB fetched by me (51 files from a pinned commit, sizes
checked), about 42 MB fetched by FluidAudio, and a 21 MB shallow clone of FluidAudio. The
brief allowed about 325 MB for the model and about 288 MB for the clone. The 87.3 MB NeMo
xcframework was not downloaded.
